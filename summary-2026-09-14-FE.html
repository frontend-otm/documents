FE System Mapผังระบบ FE 5 repos, 1 domain

Independent apps connected only by full-page navigation — no client-side routing across apps. The legacy monolith still owns My Orders/Return until cutover. แอปแยกอิสระ เชื่อมกันด้วย full-page navigation เท่านั้น ไม่มี client-side routing ข้ามแอป — legacy monolith ยังถือ My Orders/Return จริงอยู่จนกว่าจะ cutover

⚠ core-utils is not one shared package — Base uses @lk/od-core-utils, Checkout uses @lk/core-utils, Post-order/Store Locator have none at all core-utils ไม่ใช่ package เดียว — Base ใช้ @lk/od-core-utils, Checkout ใช้ @lk/core-utils, Post-order/Store Locator ไม่มี shared package เลย

1.Architecture understanding confirmedความเข้าใจด้าน Architecture ที่ยืนยันแล้ว

  • The FE system is split into 4 independent apps (Base, Checkout, Post-order, Store Locator) + a legacy monolith that hasn't been fully decommissioned yet. ระบบ FE แยกเป็น 4 แอปอิสระ (Base, Checkout, Post-order, Store Locator) + legacy monolith ที่ยังไม่ถูก decommission เต็มที่
  • Apps connect only via hard navigation (full page reload) — no client-side routing across apps. Session works via a cookie each app validates independently, with a silent fallback (no visible redirect). แอปเชื่อมกันด้วย hard navigation (full page reload) เท่านั้น ไม่มี client-side routing ข้ามแอป — session ทำงานผ่าน cookie ที่แต่ละแอป validate เอง แบบ silent fallback (ไม่มี redirect ให้เห็น)
  • Correctedแก้ความเข้าใจเดิม Return/Exchange flow is NOT active in production for OWNDAYS SG (corrects the earlier assumption that it was running via the legacy monolith). Return/Exchange flow ไม่ได้ active ใน production สำหรับ OWNDAYS SG (แก้ความเข้าใจเดิมที่คิดว่ากำลังใช้งานผ่าน legacy monolith)
  • There's no policy forcing all apps to the same Next.js/React version — the team has already accepted this. ไม่มี policy บังคับ version Next.js/React ให้ตรงกันทุกแอป — เป็นเรื่องที่ทีมยอมรับแล้ว

2.Release Process understanding confirmedความเข้าใจด้าน Release Process ที่ยืนยันแล้ว

  • Preprod deploys freely from any branch; Production requires a Tag only (REL = full 9 stages, HFX = faster hotfix). Preprod deploy จาก branch ได้อิสระ, Production ต้องมี Tag เท่านั้น (REL = ครบ 9 stage, HFX = hotfix เร็วกว่า)
  • Correctedแก้ความเข้าใจเดิม Previously understood that HFX skips Checkmarx SAST as the doc stated — confirmed the document is wrong: both REL and HFX actually run Checkmarx the same way (no security gap here). เดิมเข้าใจว่า HFX ข้าม Checkmarx SAST ตามที่เอกสารเขียนไว้ — ยืนยันแล้วว่าเอกสารเขียนผิด จริงๆ ทั้ง REL และ HFX รัน Checkmarx เหมือนกัน (ไม่มีช่องโหว่ security ตรงนี้)
  • Action itemAction item Developer-level access and above can create tags/trigger the pipeline themselves, but approval must come from designated QA + Release Owner roles only — action item: T&M needs to nominate people for these 2 roles. Developer ระดับขึ้นไปสร้าง tag/trigger pipeline เองได้ แต่การอนุมัติต้องเป็น QA + Release Owner ที่ได้รับมอบหมายเท่านั้น — มี action item ให้ทีม T&M เสนอชื่อ 2 ตำแหน่งนี้
  • Rollback works independently per app via Deployment History — no cross-app versioning contract exists, but matching release-tag names (cut on the same date) can be used as a consistency reference. Rollback ทำได้อิสระต่อแอปผ่าน Deployment History ไม่มี versioning contract ข้ามแอป แต่ใช้ชื่อ release tag (ตัดวันเดียวกัน) เป็นตัวอ้างอิงความสอดคล้องกันได้
