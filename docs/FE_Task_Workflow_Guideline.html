Frontend Task Workflow Guideline

Task naming, ownership, status transitions, feedback handling, and release flow.

แนวทางการตั้งชื่อ Task, ผู้รับผิดชอบ, การเปลี่ยน Status, การจัดการ Feedback และ Release

1. Purpose

This guideline defines a consistent workflow for Frontend implementation, feedback, production feedback, and release tasks. The goal is to keep ownership and task history clear while avoiding unnecessary task creation during the normal implementation and review cycle.

1. วัตถุประสงค์

เอกสารนี้ใช้กำหนด Workflow กลางสำหรับงาน Frontend, Feedback, Production Feedback และ Release เพื่อให้ทุกคนเข้าใจตรงกันว่าใครเป็นผู้รับผิดชอบ สามารถเปลี่ยน Status ได้ถึงขั้นไหน และควรสร้าง Task ใหม่เมื่อใด โดยไม่สร้าง Task เพิ่มโดยไม่จำเป็นในช่วง Implementation และ Review ปกติ

3. FE Task Workflow

Owner: Assigned Frontend Developer

To Do→In Progress→Done
  • The assigned Dev may move the FE task from To Do → In Progress → Done by themselves.
  • When the Dev reports that implementation is complete, the Head may review it before the Due date.
  • If the Head requests adjustments that are within the original scope and the Dev's Due date has not passed, continue using the same FE task. A separate Feedback task is not required.
  • Due date is not the only criterion. New or out-of-scope requirements should be handled separately.

3. Workflow ของ FE Task

Owner: Frontend Developer ที่ได้รับมอบหมาย

To Do→In Progress→Done
  • Dev ที่รับผิดชอบ Task สามารถเปลี่ยน Status จาก To Do → In Progress → Done ได้ด้วยตนเอง
  • เมื่อ Dev แจ้งว่า Implementation เสร็จแล้ว Head สามารถ Review งานก่อนถึง Due date ได้
  • หาก Head ต้องการให้แก้บางส่วน และยังเป็นงานที่อยู่ใน Original Scope รวมถึงยังอยู่ภายใน Due date ของ Dev ให้ใช้ FE Task เดิมต่อได้ โดยยังไม่จำเป็นต้องสร้าง Feedback Task
  • ไม่ควรใช้ Due date เป็นเกณฑ์เพียงอย่างเดียว หากเป็น Requirement ใหม่หรืออยู่นอก Original Scope ควรแยกออกจากงาน Implementation เดิม

4. Feedback / Production Feedback Workflow

To Do→In Progress→Waiting→Done
  • Dev moves the task through To Do → In Progress → Waiting.
  • Waiting means the requested changes are complete and confirmation or additional feedback is pending.
  • If the Head coordinates with JP, the Head moves Waiting → Done after JP confirms.
  • If the Dev communicates with JP directly, the Dev may move the task to Done after JP confirms.

4. Workflow ของ Feedback / Production Feedback

To Do→In Progress→Waiting→Done
  • Dev เปลี่ยน Status ตามลำดับ To Do → In Progress → Waiting
  • Waiting หมายถึง Dev แก้ไขตาม Feedback เสร็จแล้ว และกำลังรอ Confirmation หรือ Feedback เพิ่มเติม
  • หาก Head เป็นผู้ประสานงานกับ JP เมื่อได้รับ Confirmation จาก JP แล้ว Head จะเป็นผู้เปลี่ยน Waiting → Done
  • หาก Dev เป็นผู้คุยกับ JP โดยตรงโดยไม่ผ่าน Head เมื่อได้รับ Confirmation แล้ว Dev สามารถเปลี่ยน Task เป็น Done ได้เอง

5. Additional Feedback While Waiting

  • Do not create another Feedback task for the same active feedback cycle.
  • Add the new feedback to the existing task Description.
  • Create a dated heading for each round, e.g. Feedback - 2026/08/20.
  • Move Waiting → In Progress when additional implementation is required.
  • Adjust the Due date based on the latest feedback and required effort, or to a date the Head considers appropriate.

5. กรณีมี Feedback เพิ่มระหว่าง Waiting

  • ไม่จำเป็นต้องสร้าง Feedback Task ใหม่ หากยังเป็น Feedback cycle เดิม
  • เพิ่มรายละเอียด Feedback ใหม่ใน Description ของ Task เดิม
  • แยกหัวข้อตามวันที่ให้ชัดเจน เช่น Feedback - 2026/08/20
  • หากต้องแก้เพิ่มเติม ให้เปลี่ยน Waiting → In Progress
  • ปรับ Due date ตาม Feedback ล่าสุดและ Effort ที่ต้องใช้ หรือใช้วันที่ Head พิจารณาว่าเหมาะสม

7. Quick Decision Rules

SituationAction
Dev is implementing the original scopeUse FE task.
Head asks for an in-scope adjustment before Due dateKeep using FE task; no Feedback task needed.
New / out-of-scope requirementHandle separately.
Feedback is Waiting and JP sends more feedbackUpdate Description, adjust Due date, and return to In Progress.
Head coordinated with JP and JP confirmsHead moves task to Done.
Dev coordinated directly with JP and JP confirmsDev may move task to Done.
Feedback arrives after Production releaseCreate Production Feedback task.
Production Feedback fix needs deploymentCreate a new Release task for the fix.
